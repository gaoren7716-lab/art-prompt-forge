# 编码手册

全库 779 条可引用条目、15 个段码、306 条带编码的关系边。

这一层解决三件事：**要看有哪些类型**（段码总表）、**要单独取某一块**（编码或中文名）、**要组合**（编码串）。

打开 `index.html` 顶栏的「编码工作台」可以直接查、可以组，产出规范组合串与 spec。

## 段码总表

**全库只有一种编码形态**：`段码-三位`，段码固定两字母。
段码只表示归属（这是哪一层），不夹带国别/类别/分组 —— 理由见下一节。

| 段码 | 名称 | 条数 | 可直接组合 | 说明 |
| --- | --- | --- | --- | --- |
| `PA` | 画家 | 205 | 205 | 205 位，国别与生卒年见字段 |
| `MV` | 流派 | 64 | 64 | 64 个艺术运动与风格 |
| `WK` | 名画 | 104 | 104 | 104 幅有据可查的具体作品 |
| `MD` | 媒介 | 28 | 28 | 28 种材料与技法 |
| `SJ` | 题材 | 26 | 26 | 26 类画面内容 |
| `RL` | 关系 | 306 | —（事实说明） | 306 条边：师承/影响/收藏/使用 |
| `AT` | 原子模块 | 126 | 126 | 126 条，12 类，类别见条目详情 |
| `OP` | 光学词条 | 84 | 84 | 84 词，10 组，所属组见条目详情 |
| `OG` | 光学分组 | 10 | 0 | 10 组，分组本身不进提示词 |
| `TK` | 任务模板 | 13 | 0 | 13 类创作诉求与验收标准 |
| `SG` | 签名卡 | 25 | 0 | 25 张调好的完整配方 |
| `OR` | 变形算子 | 38 | 38 | 38 个受控变形规则，类别见条目详情 |
| `CF` | 冲突规则 | 21 | 0 | 21 条四级裁决规则 |
| `MT` | 模型实测 | 12 | 0 | 12 份实测记录，换模型前必看 |
| `PV` | 来源许可 | 23 | 0 | 23 条来源与授权登记 |

**为什么区分「可直接组合」**：不是所有条目都能进提示词。
签名卡是一整套已配好的配方（该套用而非往里加词），任务模板是流程起点，
冲突规则由引擎自动裁决，来源许可与模型实测是查证用的。
把这些塞进提示词不会报错，只会让结果莫名其妙 —— 所以解析器在 `toSpec()` 阶段就挡掉它们，并在界面上标出「不进提示词」。

## 为什么砍掉了分类段

上一版有四种长度并存：

| 旧形态 | 例子 | 中段的含义 |
| --- | --- | --- |
| 三段 | `P-IT-007` | 画家：**国别**字母 |
| 两段 | `AM-101` | 原子模块：**类别**数字 |
| 三段 | `AM-A-001` | 原子模块：**类别**字母 |
| 三段 | `O-01-001` | 光学词条：**分组**号 |

问题不在于「多了一种」，而在于**同一个位置放了三种不同的语义**。
语法相同、含义不同，于是 `AM-101` 与 `O-001` 肉眼几乎无法区分，
而 `AM-101` 与 `AM-A-001` 又同段不同形。组合串一旦长起来，
人眼无法校验，机器也无法用一条正则解析全库。

现在国别/类别/分组降级为**字段**，靠界面筛选与检索取回。
理由：塞进编码会让编码长度不可控，而组合时要的是「能打出来」，
不是「能看出分组」。光学分组单列 `OG` 段 —— 它与词条挤在同一段时，
「OP-001 是组还是词」永远说不清。

### 两条硬约束

1. **段码与该段旧 ID 的形态必须不相交**。原子模块段用 `AT` 而不是 `AM`
   就是这个原因：旧 ID 恰好是 `AM-101` 这种形态，若新码也叫 `AM-001`，
   字符串 `AM-101` 会同时是「某人的旧 ID」和「别人的新码」，解析给谁都不对。
   `check_codes` 有一条断言专门守这个。
2. **段码互不为前缀**。若 `P` 是 `PA` 的前缀，`P-001` 会被误判成 PA 段。

### 序号

数字位恒为三位。画家 205 位、原子模块 126 条、关系边 306 条，
两位撑到 99 就撞号；三位可到 999，中途新增只往后追加，不会重排旧号。

序号**不保证连续**：`PV` 段就是 `PV-001~008`、`PV-020~023`、`PV-030~040`。
这是跟着旧 ID 走的必然结果 —— 为了连续而重排会让来源许可的引用与历史记录脱节。

**code 一旦发布不可改**。改它等于让用户手里的组合串失效。
改中文名不影响 code 解析 —— 解析走映射表，不读数据源的 `zh`。

## 八路解析

同一个条目有八个入口，都能命中：

| 输入 | 例子 | 说明 |
| --- | --- | --- |
| 规范编码 | `PA-125` | 唯一、可排序、机器友好 |
| 旧 ID | `P-IT07` | 历史主键，向后兼容 |
| 上一版编码 | `P-IT-007` | 已对外发布过，继续能查 |
| 省略零位 | `PA-7` | 只在已存在的编码上生效 |
| 中文名 | `达·芬奇` | |
| 英文名 | `Caravaggio` | |
| 光学英文词 | `chiaroscuro` | 横切词条专有入口 |
| 常用短码 | `CC0` `SD1.5` `MJ v7` | |

**缺零位只对已存在的编码生效**：`PA-7` 能查到第 7 位画家，
而 `PA-999` 会明确报不存在 —— 不会凭空造一个号。
（若补零写成「补完再查表」，某段超过 999 条时序号会静默回绕到别人的号上。）

**查不出来时必须说「找不到」并给最接近的候选，绝不返回一个猜测。**
宁可让你重输，也不能给你一个假编码 —— 假编码会一路错到出图那一步才暴露。

**同一 code 只保留第一次出现**。写 `P-IT07 + PA-125` 不会重复计入，
而是在 `dupList` 里回传「已合并」—— 不去重的话配方里同一个零件会出现两遍，
权重被算成 2.0，效果与用户意图完全不同，而界面上看不出任何异常。

## 组合串

多项用 `+` 或逗号分隔，编码与中文名可混写，新旧写法也能混着写：

```
PA-125 + 明暗对照 + 单侧窗光 + OP-004
达·芬奇 + 黄金时刻
P-IT07 + PA-125 + 明暗对照
```

最后一行前两项指向同一位画家，会合并成一项 —— 混用旧写法不会把配方写重。

空格也能当分隔符，但有一处例外需要知道：本库有一批名字自带空格
（`SD 1.5`、`CC0 1.0 公共领域奉献`），解析器会做贪心回溯把它们当整体，
所以 `PA-125 明暗对照 单侧窗光` 能正确拆成三项。

串里错一项时**整体报失败**并精确指出是哪一项，同时把正确项单独返回，
你可以改掉错的那项继续用 —— 不会因为一个笔误丢掉整串。

## 关系边的编码

306 条关系边也各有编码（`RL-001` ~ `RL-306`），
全局连续编号而不是按类型各起一份 —— 按类型编号会让 8 种类型互相撞码，
306 条边实际只剩 104 个不同编码，`RL-001` 指向哪条边就说不清了。

边的类型信息不靠编码承载，靠 `kind` 字段筛选。
关系边不进提示词 —— 它们是「这条边存在」的事实说明，不是可拼装的零件。

## 每条编码对应的提示词

**`codes.json` 回答「这条是谁」，`prompts.json` 回答「这条是什么词」。**
两份必须一起给：只有编码没有词，组合这件事仍然做不成。

提示词不是手写的，全部由 `FORGE.compose()` 现算 —— 一旦在这里手写词面，
它就会和引擎的冲突裁决各说各话，且引擎一改就全部漂移。

### 三档完整性

| 档 | 条数 | 含义 |
| --- | --- | --- |
| `full` 可直接出图 | 465 | 题材 / 画家 / 流派 / 名画 / 媒介 / 签名卡 / 任务模板。自带主体或主体足够明确 |
| `part` 零件，需搭配基底 | 248 | 原子模块 / 光学词条 / 算子。它们改的是别人的画面，单独投放只剩一句约束词 |
| `none` 不进提示词 | 66 | 来源许可 / 模型实测 / 冲突规则 / 光学分组。另有 306 条关系边同样不进 |

**为什么零件要单列一档**：`AT-001` 单独跑出来的 `tags` 就是
`chiaroscuro, masterpiece, best quality, ...` —— 一条约束词加一堆画质词，
拿去出图几乎等于没约束。所以 `part` 额外给一份 `withBase`：
挂在写死的演示基底「单人肖像（题材里最中性的一条）」上跑通，让人看到它正常怎么用。
基底是公开写死的演示件，不是推荐配方 —— 偷偷配基底会让用户
以为原子模块本身就是完整配方。

**为什么 `none` 要写清原因**：给一个空文本框等于暗示「这里本来有词但被清了」。
所以这一档只给一句话理由，比如 PV 是授权登记、MT 是模型实测、CF 是引擎裁决规则。

### 界面与命令行

打开 `index.html`：

- 编码工作台的每条解析结果、段码总表的每一行，都带一个「看提示词」按钮
- 主界面配方盘里每个零件也带一个「词」按钮，点开直接跳到工作台并展开那一条
- 面板内可切 SD / MJ / Flux / 自然语言四种权重写法，切换只改语法不改词数

同一份词面在四个平台上写法不同（`(词:1.00)` / `词::1.00` / `词 词` / 裸词），
不标出来用户复制出去在别的平台上直接跑不通。

命令行查单条：

```bash
node tools/show_prompt.js PA-125              # 规范编码
node tools/show_prompt.js 达·芬奇              # 中文名
node tools/show_prompt.js AT-001 --platform mj # 换平台写法
node tools/show_prompt.js PA-125 --json       # 机器可读
```

## 给下游的接口

```bash
node tools/check_codes.js     # 42 项编码体检
node tools/show_prompt.js      # 查单条提示词
```

导出产物：

| 文件 | 内容 |
| --- | --- |
| `dist/codes.json` | 779 条编码对照，含层级、是否可组合、别名 |
| `dist/code-segments.json` | 15 个段码的规模与可组合数 |
| `dist/relations.json` | 306 条关系边，已带 `code` |
| `dist/prompts.json` | 779 条编码对应的 `tags` / `neg` / `gpt`，附 `explain`（效果说明）与 `zhGpt`（中文对照），零件另附 `withBase` |
| `dist/model-capabilities.json` | 12 个模型的词面策略 / 参数甜区 / 垫图兜底建议 |

各单表导出（`painters.json` 等）的每条记录也都带 `code` 字段，
由 `assets/codes.js` 的纯函数在导出时挂上 —— 派生规则只有一个真源，不会与数据漂移。

`prompts.json` 单独成文件而不塞进 `all.json`：它超过 1 MB，
混进去会把 `all.json` 撑成人眼读不了、脚本也不必要整体加载的大文件。
